# Epic 2 Wave 2 + Epic 3 — Guided Conversation Design Spec

**Status:** self-approved under the standing autonomous-loop authorization (no human review gate for this spec pass — explicit user instruction this session: proceed through the entire backlog without stopping between epics/waves).

**Scope:** Epic 2 Wave 2 (BLD-06.2, BLD-06.3, BLD-06.4, BLD-06.5, BLD-06.9) plus Epic 3 (E3.1, E3.2, E3.3, E3.4). These are grouped in one spec because they share one real mechanism — the `CodyChatPanel` shipped in Wave 1 — and because E3.1 (idea entry as a chat) is architecturally the same "Cody chat drives a step" pattern BLD-06.2/06.3 apply to every later step, just occurring one step earlier in the funnel, before signup.

## Codebase reality (confirmed by direct reads + one verified investigation fork; a second fork's report was partially unreliable — see note below — and every claim from it used here was independently re-verified by direct file reads before being relied on)

- **Real artifact generation**: `POST /api/build/artifact` (`app/api/build/artifact/route.ts`), called from `lib/build/useAutoplay.ts` (autoplay's generation loop) and `components/build/ArtifactFrame.tsx` (manual regenerate). Body: `{view, idea, track, companyName?, prior?, feedback?, companyId?}`. Uses `lib/build/claude-completion.ts`'s `getClaudeCompletion()` (Bedrock → direct Anthropic provider chain, already real and working).
- **Revision-from-feedback already works today**: `lib/build/artifact-edit.ts`'s `feedbackInstruction(feedback)` appends free-text founder feedback to the regeneration prompt; `collectPrior(seq, generated, excludeView)` collects every other already-generated artifact as context. `ArtifactFrame.tsx`'s `runRegenerate()` (lines ~80-117) is the real, shipped, working wiring: opens a "What should change?" textarea, POSTs to `/api/build/artifact` with `feedback` + `prior`, dispatches `GEN_DONE` on success. **This is the mechanism BLD-06.3 builds on — Cody asking structured questions and composing the answers into that same `feedback` string, rather than requiring free text from the user.**
- **"Answers carry into later steps" already works today**: `useAutoplay.ts` builds `prior` from `state.generated[v]` for every already-generated view in the track sequence, passed into every `/api/build/artifact` call. This is BLD-06.5's literal mechanism, already live — no new context-passing system needed.
- **No artifact-content version history exists anywhere.** `lib/build/version-store.ts` is Railway *deployment* rollback history — wrong domain, not reusable as data, though its ZeroDB-scoped `{owner, company}` shape is a reasonable pattern to mirror. `document-store.ts`'s `upsertDocument` is confirmed overwrite-only (its own doc comment says so). **BLD-06.4 needs real new design** — covered below.
- **`CodyNudge.tsx`** (23 lines) — a real, shipped "ask before doing something, wait for accept/dismiss" UI/state pattern (`nudgeState` in `BuildState`, `NUDGE` dispatch), but with static per-view copy from `PRIMITIVE_MAP`, not Cody-generated prose. Reused as the state/UI precedent for BLD-06.9, not reused verbatim (BLD-06.9's copy must be real, LLM-generated, per-build text, not a static map).
- **`Intake.tsx`** (confirmed by direct read, 137 lines) is a plain textarea + button form today. Its real submit flow (`start()`): fires `trackEvent('idea_submitted', ...)`, calls `/api/build/brand` to name the company, then either `DEFER_BUILD` (anonymous — stash via `pending-build.ts` and route to signup) or `START_BUILD` (already authenticated) — directly, with **no kickoff-question step anywhere between idea and generation**. E3.1 replaces this screen's UI; E3.2/E3.3 insert a real new step between brand-naming and `START_BUILD`.
- **`lib/build/pending-build.ts`** (confirmed by direct read) — pure `localStorage`, key `ainative_pending_build`, no expiry/TTL field at all. This is the real mechanism behind **BLD-03** ("pre-sign-up idea attaches to the new account", already shipped this session under a different literal issue number but functionally identical to what BLD-03 asks for — confirmed by its own doc comment: "stash the generated idea/brand and send them to signup... the deferred START_BUILD still fires"). E3.4 explicitly "shares storage with BLD-03" per the backlog doc — meaning E3.4 extends this SAME mechanism with real server-side persistence, not a parallel system.
- **`lib/build/active-build.ts`** (confirmed by direct read) — separate, post-signup, localStorage-only pointer (`{slug, screen}`) gated by `canResumeActiveBuild` (a real session check, from this session's Epic 1 memory of issue #948). Distinct from `pending-build.ts`; not what E3.4 extends.
- **No kickoff-question UI exists anywhere** (confirmed: zero matches for "kickoff" or either track's literal question text, across `components/` and `lib/`). E3.2/E3.3 are genuinely new screens.
- **Existing cron pattern**: `app/api/cron/{alerts,comms-digest,winback,loop-backfill}/route.ts` — each a `GET` handler wrapping a dry-run-capable sweep function. A new 30-day draft-purge cron follows this exact shape.
- **Note on fork reliability**: one investigation fork (Epic 3 infra) returned its report with zero recorded tool uses and a flagged rate-limited safety classifier — a signal its claims might be unverified. Every substantive claim from that fork used in this spec (`pending-build.ts`'s real shape, `active-build.ts`'s real shape, the absence of kickoff UI) was independently re-read and confirmed directly before being relied on here; two specific inaccuracies in that fork's report (a claimed `savedAt` field on `PendingBuild` that does not exist; an overstated `active-build.ts` payload shape) were caught and are NOT carried into this spec.

## Design

### BLD-06.2 — Cody summarizes each step (3 pts)

New, small LLM call: `summarizeArtifactStep(view, track, generatedContent)` in a new `lib/build/cody-chat.ts` module, using the same `getClaudeCompletion()` provider chain `/api/build/artifact` already uses (never a new model/endpoint). System prompt: produce 3 sentences or fewer, plain language (no jargon list words — reuses the project-wide plain-language rule this session has applied everywhere), explaining what this step is and why it matters. New route `POST /api/build/cody-summary` (thin wrapper, same auth posture as `/api/build/artifact`). `CodyChatPanel` calls this once when `state.view` changes and a real summary doesn't already exist for that view+content combination this session (cache in component state, not persisted — a page reload re-summarizing is acceptable, cheap, and avoids a new persistence surface for throwaway text).

### BLD-06.3 — Cody asks questions and revises as a draft (8 pts)

Per-artifact question sets are real content decisions (what to ask about `thesis` differs from `wedge` etc.) — out of scope to hand-author all of them in this pass given the scale of the full track list (7 Company-track + 14 App-track artifacts); this story ships the REAL mechanism plus real question sets for the artifacts with the clearest "ASSUMPTION · TBD" pattern already visible in generated content (confirmed present in generated artifact text via a direct read of a real generated `thesis` artifact's `genContent` during this session's earlier Company-track verification — e.g. placeholder assumption markers). Mechanism:
- `CodyChatPanel` gains a real question-asking mode: up to 3 questions per step (component state, not persisted), each with 2-4 tap-to-answer suggestions plus a free-text option and an always-present "Not sure yet" (matching the backlog doc's own UI contract verbatim).
- On answering at least one question, the panel composes a feedback string from the Q&A pairs (`"The founder answered: Q: ... A: ..."` for each answered question) and calls the SAME `runRegenerate`-shaped request `ArtifactFrame.tsx` already makes — `POST /api/build/artifact` with `feedback` set to the composed string and `prior` via the existing `collectPrior`. This reuses the exact shipped revision mechanism; no new generation endpoint.
- Result renders as a draft (the existing `GEN_DONE` dispatch already does this — content replaces in place; "draft" vs. "saved" is BLD-06.4's distinction, layered on top, not reinvented here).
- "Keep as is" (user declines all questions) leaves the artifact unchanged and does not call the regenerate endpoint at all.

### BLD-06.4 — Save from chat, version history, restore (5 pts)

Genuinely new. A new ZeroDB table `builder_artifact_versions` (mirrors the `ensureTable`-then-write idempotent-create pattern established in `otp.ts`/`funnel-events.ts` — never a different mechanism for the same class of problem), one row per saved version: `{companyId, view, content, savedAt, label?}`. A new `lib/build/artifact-versions.ts` module: `saveArtifactVersion(companyId, view, content)`, `listArtifactVersions(companyId, view)`, `restoreArtifactVersion(companyId, view, versionId)`. "Save this" (typed in chat or a Save button on Cody's message) calls `saveArtifactVersion` with the artifact's current `state.generated[view]`; the existing `EDIT_ARTIFACT`/`GEN_DONE` dispatches already update the live artifact, so "becomes the current version" is just: save BEFORE the next regenerate overwrites it (an unsaved draft moving to the next step without saving is BLD-06.4's own explicit "Cody asks whether to save it or keep the last saved version" scenario — a confirm-style prompt in the chat panel, gated on an `isDraftUnsaved` flag the panel already has visibility into via `state.generated[view]` having changed since the last save).

### BLD-06.5 — Answers carry into later steps (3 pts)

No new mechanism — confirmed already real via `prior`/`collectPrior`. This story's actual work is verifying + testing that BLD-06.3's composed Q&A feedback, once it has driven a save (BLD-06.4), genuinely appears in `state.generated[view]` and therefore flows into the next step's `prior` the same way any other saved artifact content already does. A real integration test proving this chain (answer → regenerate → save → next-step generation request includes it in `prior`) is this story's actual deliverable, not new production code.

### BLD-06.9 — Cody explains before building (2 pts)

Reuses `CodyNudge`'s accept/dismiss UI/state pattern (`nudgeState`, `NUDGE` dispatch) but with real, LLM-generated copy via the same `getClaudeCompletion()` chain as BLD-06.2 (not `PRIMITIVE_MAP`'s static text) — one short message naming what will be built and which business goal it tests, shown before build-type screens (`swarm`/`infra`/`preview` views, confirmed from `lib/build/state.ts`'s `APP_VIEWS` to be the real build-stage artifacts) begin, blocking generation until accepted.

### E3.1 — Idea entry becomes Cody's first message (5 pts)

`Intake.tsx`'s plain form becomes a chat: Cody's first message is "Tell me your idea in a sentence or two. I'll ask 3 quick questions, then get to work." (verbatim from the backlog doc), a single free-text input area styled as a chat turn (reusing `Live.tsx`'s `.m-chat-cody` CSS classes as the established visual pattern for chat-in-this-app, confirmed real and already styled). On submit, the SAME real `start()` logic in `Intake.tsx` runs unchanged (brand naming, auth-wall defer-or-build decision) — this story changes presentation, not the underlying submit mechanics, which already work correctly. "Idea too thin" (single word) triggers one Cody follow-up question before proceeding — a small new check (`idea.trim().split(/\s+/).length < 2`) gating a real LLM-generated clarifying question via the same provider chain.

### E3.2 / E3.3 — Kickoff questions (5 + 3 pts)

A new screen (`KickoffQuestions.tsx`), inserted between `Intake.tsx`'s brand-naming step and the `START_BUILD`/`DEFER_BUILD` dispatch. One question per message (matching the backlog doc's exact UI contract: tap-to-answer suggestions + free text + "Not sure yet" on every question), the real question sets and feed-targets specified verbatim in the backlog doc's own tables for E3.2 (Company, 3 questions by track-variant: new business vs. growing) and E3.3 (App, 3 questions). Answers are stored in `BuildState.answers` (confirmed to already exist as a tracked field per this session's earlier build-context reads) and threaded into the FIRST artifact's generation request as additional `feedback`-shaped context (reusing the same composition pattern BLD-06.3 establishes, applied once at kickoff instead of per-step) — so E3.2/E3.3 do not invent a second answer-carrying mechanism; they produce the first set of answers that flow through the one BLD-06.5 confirmed already works.

### E3.4 — Anonymous draft autosave and resume (5 pts)

Extends `pending-build.ts`'s real, already-shipped mechanism with genuine server-side persistence: a new ZeroDB table `builder_anon_drafts`, keyed by a random browser-scoped token (set as a cookie on first kickoff-question interaction, not keyed by IP or any PII), storing `{token, idea, track, answers, step, updatedAt}`. `pending-build.ts`'s existing localStorage write stays as the same-browser fast-path; a new `lib/build/anon-drafts.ts` module (`saveAnonDraft`, `loadAnonDraft`, mirroring the same idempotent-create ZeroDB pattern) adds the server-side counterpart so "resume where you left off" can survive a cleared localStorage / return visit without the cookie's underlying browser profile being wiped. A new cron `app/api/cron/purge-anon-drafts/route.ts` (same `GET` + dry-run-capable sweep shape as the 4 existing cron routes) deletes rows older than 30 days, stated to the user when they first see the kickoff flow (confirmed this is the backlog doc's own disclosure requirement, same pattern as BLD-18.1's US-assumption disclosure this spec's later Epic 5 work will also need).

## Review Focus

- A founder who answers ZERO kickoff questions (all "Not sure yet") must still reach generation — kickoff questions are never a hard gate, matching E3.2's own "When they answer or skip them, generation starts" scenario.
- BLD-06.3's composed Q&A feedback string must never silently exceed `FEEDBACK_MAX_CHARS` (2000, an existing real constant in `artifact-edit.ts`) in a way that truncates mid-question — compose then clip at the whole-question boundary, not mid-sentence.
- BLD-06.4's "unsaved draft, moving to next step" prompt must not block forward navigation outright — per the backlog doc's own scenario, Cody ASKS (save or keep last saved), it does not refuse to advance.
- BLD-06.9's build-start explanation must gate on the REAL build-stage views (`swarm`/`infra`/`preview`), not accidentally gate every artifact view (which would make BLD-06.2's lighter per-step summary and BLD-06.9's heavier pre-build confirmation collide on the same views).
- The anon-draft cookie token (E3.4) must never be logged, must not appear in URLs, and the purge cron must genuinely delete (not soft-delete-and-keep) rows past 30 days — matching the explicit retention promise shown to the user.
